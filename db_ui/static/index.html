Read from top to bottom. Dashed groups show overlapping work; join notes identify what must finish before continuing. This is a code map, not a measured trace. Expand a block for details.

Source-direct mode

With mainnet.skip = true, only the validated inbound pool is used. Missing or invalid source pools stop the copy. Output minimums use the source trade ratio and configured slippage; fee instructions use a fixed priority price. Quote engines, alternative-route discovery, fee-estimation RPC, transaction-fee RPC, and simulation are skipped. Required account reads, signing, sending, confirmation, and reconciliation remain. Instruction building is timed as route_instruction_build_ms; skipped quote, simulation, and dynamic-fee timers are absent. The detailed flow below describes normal mode.

Awaited async

I/O yields to other tasks, but this trade waits for its result.

Concurrent

Operations make progress during overlapping time. This does not imply separate CPU threads.

Sync work

Local computation runs inline before this task continues.

Background

A separate task runs without this trade awaiting each operation.

01 Receive & queue

Recorded timings ingestion_queue_ms — payload receipt to worker start, including decoding, journaling, and queue wait. database.record_observation — journal write.

Sync workDecode stream payload

Construct the observation locally from the incoming transaction.

Awaited async · sequentialJournal → enqueue

record_observation finishes before the observation enters the bounded execution queue. A full queue waits for capacity. The source then awaits update_cursor, which may overlap the worker.

Worker handles one observation at a time, through confirmation and reconciliation.

02 Prepare the trade

Recorded timings preparation_ms — worker start through policy checks, initial reads, sizing, input balance check, and attempt reservation. source_pool_read_ms — source prefetch request; it may continue into routing. DB operations: mark_intent, reserve_attempt, and mark_skipped on an early exit.

Sync workDecode intent & check policy

Reject stale signals and unsupported or disallowed trades before continuing.

Concurrent · awaitedWrite intent

mark_intent runs alongside the initial RPC reads. Its write must succeed before reserving or routing.

Concurrent · awaitedInspect mints + SOL balance

Mint safety inspection and the native SOL input balance read overlap. Token input balance is read later, after mint inspection and sizing.

Concurrent · deferred waitPrefetch source pool

When a source hint exists, fetch while initial reads run. Preparation does not wait for a slow prefetch; routing resumes the shared fetch if needed.

Join intent write + initial reads → size trade → check input balance.

Awaited async · required gateReserve attempt

reserve_attempt must succeed. A duplicate reservation ends this attempt before submission.

03 Build a route

Recorded timings route_ms / route_latency_ms — routing through candidate validation in section 04, excluding discovery-only waits. discovery_ms — time waiting only for discovery. source_route_ms — the source-pool attempt, including its preparation and validation. Individual operations are labeled below.

Concurrent · awaitedSource validation → quote

Wait for any remaining source fetch, validate the pool, then read adapter state and construct swap instructions. If the source fails, try cached routes and discovery; alternative candidates can race.

Timing route_source_pool_fetch_ms: remaining source fetch wait plus validation; excludes prefetch time already spent. route_quote_ms: adapter state reads, quote calculation, and swap instruction construction.

Concurrent · awaitedATA lookup + cached blockhash

ATA lookup uses RPC. A fresh blockhash comes from memory; a cold or stale cache requires an RPC refresh. These operations overlap candidate preparation, and mainnet candidates share their results for this attempt.

Timing route_shared_preparation_ms: the combined wait for ATA lookup and blockhash lookup/refresh.

Concurrent · deferred waitPrefetch SOL & output balances

Start balance reads at route entry, overlapping source validation, discovery, and quoting. Candidates share one successful snapshot within this attempt; balances are never reused across trades. Final checks wait for any unfinished reads.

Timing route_balance_prefetch_ms: early balance reads for this attempt. Any remaining wait is also included in final checks.

Join quote + ATA/blockhash preparation before estimating fees. Balance prefetch can continue until final checks.

Awaited async · sequentialEstimate priority fee

The candidate's provisional transaction is used to request its fee estimate. This request is still on the send path.

Timing route_fee_estimation_ms: transaction-specific fee estimation and fee instruction construction.

Sync workBuild & sign transaction

Apply fee instructions and sign the exact transaction that will be simulated and sent.

Timing Included in route_ms; signing has no separate recorded timer.

04 Validate the candidate

Recorded timings route_simulation_ms and route_final_checks_ms overlap and are included in route_ms. They are not extra sequential stages.

Concurrent · awaitedExact simulation

Simulate the signed transaction. A simulation failure rejects the candidate.

Timing route_simulation_ms: simulation of the exact signed transaction.

Concurrent · awaitedFee & balance checks

Look up the exact transaction fee while using the prefetched balance snapshot or waiting for unfinished reads. A failed SOL prefetch is retried here. Verify SOL covers the swap, fee, and tip. These checks overlap exact simulation.

Timing route_final_checks_ms: exact fee lookup, waiting for or retrying the balance snapshot, and the SOL funds check.

Both must pass before a candidate can win.

05 Send & persist

Recorded timings post_route_ms — winner handling and serialization up to send start. sender_request_ms — submission request through response. post_send_journal_ms — route and signed-transaction writes after the response.

Send starts here receipt_to_send_start_ms
Awaited asyncSender request

Submit and wait for the response. receipt_to_send_response_ms includes this wait; send-start latency does not.

Timing receipt_to_send_start_ms and receipt_to_send_response_ms are cumulative times from payload receipt, not durations to add together.

Awaited async · after submissionSave route → save signed transaction

mark_route and persist_signed run after the sender response, including errors. Journal failures are logged and confirmation continues. A crash before persistence can leave the submitted signature missing from local recovery data. SQLite retains WAL with full durability.

06 Confirm & finish

Recorded timings confirmation_ms — confirmation polling and landing-slot persistence. reconciliation_ms — resulting balance reads, debit/output checks, and outcome persistence. DB operations: record_landed_slot, update_attempt. Logging and timing-writer enqueue have no separate stage timer.

Awaited async · sequentialConfirm → record slot → reconcile → save outcome

The worker waits for confirmation, persists the landing slot, checks resulting balances, and saves the outcome. These steps delay the next observation, not this trade's send start.

Sync workLog timings & try enqueue

Console logging is synchronous. Timing JSON is offered to the background writer with a nonblocking queue operation. Then the worker can process its next observation.

Alongside the worker

BackgroundTiming writer

A separate task awaits database commits. It batches up to 32 available records from a 256-record queue. The trade does not await these writes.

Queue overflow or write failure can drop telemetry with a warning. Pending timing records can be lost at process shutdown. Recovery data never uses this queue.

Timing No per-trade timer for background telemetry writes. db_total_us sums measured DB operations; db_pre_send_us snapshots that sum before sending, and db_post_send_us is the remainder. These are overlapping operation totals, not wall-clock stages.

BackgroundPool catalog refresh

Periodic maintenance refreshes routing candidates independently of the execution worker.

Timing No separate per-trade timer for background catalog maintenance.

BackgroundBlockhash cache refresh

Warm the cache before signal and execution workers start, then refresh one second after each completed refresh. Fetch confirmed blockhash and block height together, with a 1.5-second timeout and more than 20 blocks of remaining validity.

Entries expire two seconds after request start. Failed refreshes do not extend freshness; a cold or stale trade-time lookup waits for RPC. Fresh lookups do not wait for background refresh. Maintenance stops with the service.

Timing No separate per-trade timer for background refresh. A trade waiting on a cold/stale cache records that wait in route_shared_preparation_ms.

BackgroundSender connection warming

Mainnet startup warms the Sender connection. Periodic pings then run alongside the worker, waiting 30 seconds between completed warmups.

Timing No separate per-trade timer for startup warmup or background pings.

Reading the timings

Use receipt_to_send_start_ms to compare send latency. DB and route substage durations can overlap; adding them does not reconstruct a timeline. Route substages sum work across attempted candidates, including failures and cancellation. Unstarted timers are omitted; older records may lack newer fields. DB operation entries contain elapsed microseconds and call counts; other fields use milliseconds unless labeled _us.

route_balance_prefetch_ms measures the early balance reads. route_shared_preparation_ms includes ATA lookup and blockhash lookup, with RPC refresh only on a cold or stale cache. Final-check time includes any remaining balance wait and the transaction fee check.
